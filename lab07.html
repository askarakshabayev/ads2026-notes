Merge Sort

Two O(n log n) sorts already exist, so this one has to justify itself. It does, twice: it is the stable one, and its merge step counts things that sorting alone cannot — which is the first genuinely new idea in three weeks.

01

The whole algorithm is here

16 min demo: merge

What to say

  • Do not start with the sort. Start with the sub-problem: two already sorted arrays, produce one sorted array. Everything else today is this, wrapped in recursion.
  • Two indices, compare the fronts, take the smaller, advance that one. Each element is looked at once, so the merge is O(n + m) — say this, because students expect a nested loop.
  • Run the demo and point at the counter: merging two arrays of 1000 costs 2000 steps, not a million.
  • Then the tail. One array runs out first and the rest of the other is appended as a block. Forgetting that block is the single most common bug in this lab — it passes the samples and fails everything else.
  • And the line that makes it stable: when the fronts are equal, take from the left array. Change <= to < and stability is gone, silently.

02

Wrap the merge in recursion

18 min board

What to say

  • Split in half, sort each half, merge. Three lines. The base case is a single element, which is already sorted.
  • Draw the recursion tree for eight elements. log n levels, O(n) work per level — that is where n log n comes from, and it is visible on the board rather than asserted.
  • Unlike quicksort, the split is positional — always the middle, never data-dependent. That is exactly why there is no bad input and no O(n²) day.
  • The price is memory: the merge needs a buffer of size n. Say it plainly — this is the only sort so far that is not in place, and on a 256 MB limit with 10⁶ ints it is still fine.
  • Allocate the buffer once, outside the recursion. A vector created inside merge turns O(n log n) into something much worse in practice, and it is the usual reason a correct solution times out.

For the board

void mergeSort(int l, int r) {   // [l, r)
    if (r - l < 2) return;
    int m = l + (r - l) / 2;
    mergeSort(l, m);
    mergeSort(m, r);
    merge(l, m, r);
}
void merge(int l, int m, int r) {
    int i = l, j = m, k = l;
    while (i < m && j < r)
        buf[k++] = (a[i] <= a[j]) ? a[i++] : a[j++];
    while (i < m) buf[k++] = a[i++];   // the tails
    while (j < r) buf[k++] = a[j++];
    for (int t = l; t < r; ++t) a[t] = buf[t];
}
Copy back, or use the buffer as the source next time. Forgetting the final copy leaves the sorted data in buf and the original untouched — and the samples, being tiny, may still look right.

Why stability is not a detail

Sort a list of students by score, having already sorted it by name. With a stable sort, equal scores stay in name order and you have a two-key sort for free. With std::sort the second pass scrambles the first.

That is the whole reason std::stable_sort exists, and it is merge sort underneath — it even allocates a buffer, and falls back to a slower in-place merge if allocation fails.

unstable: (Ann, 5) (Bob, 5) → (Bob, 5) (Ann, 5)
stable  : (Ann, 5) (Bob, 5) → (Ann, 5) (Bob, 5)
Problem A is exactly this. Sort strings by length, equal lengths keeping input order. A plain sort with a length comparator gives the right lengths and the wrong order within them — and the statement says so explicitly.
03

The merge counts things

22 min demo: inversions

What to say

  • Now the idea that makes this lecture worth more than a third sorting algorithm. An inversion is a pair i < j with a[i] > a[j] — a measure of how unsorted an array is.
  • Counting them by brute force is O(n²). At n = 10⁵ that is 10¹⁰ and hopeless.
  • The observation, and it is the one to draw: during a merge, when you take an element from the right half, it jumps ahead of everything still left in the left half. Each of those is an inversion. Add (m − i) and continue.
  • Nothing else changes. The sort is unmodified; one counter is added inside the merge. O(n log n) total.
  • The answer does not fit in int. Maximum inversions is n(n−1)/2, about 5·10⁹ at n = 10⁵. Use long long. This is the intended trap in problem D and it is worth stating twice.
  • Point at the family this opens: the same trick counts pairs with a[i] > 2·a[j], or sums of distances, or anything else expressible as "pairs across a split".

For the board

long long inv = 0;      // NOT int

while (i < m && j < r) {
    if (a[i] <= a[j]) buf[k++] = a[i++];
    else {
        inv += m - i;        // ← the only new line
        buf[k++] = a[j++];
    }
}
max inversions = n(n−1)/2 ≈ 5 · 10⁹ at n = 10⁵
Why m − i and not 1: the left half is sorted, so if a[i] is already greater than a[j], then so is every element after it. All of them are inversions with a[j], counted in one go.

Lab 7 — how it maps onto today

12 min ADS-Lab-07

What to say

  • Five problems, and they line up with the beats one to one. B is the bare merge from beat 01; A is the stable sort from beat 02; D is the inversion count from beat 03.
  • B is the warm-up — two sorted arrays in, one out. Fifteen lines. Do it in the room if there is time.
  • E looks like a sorting problem and is not: the squares of a sorted array form two already sorted runs — the negatives descending and the non-negatives ascending. Merge them in O(n) instead of sorting in O(n log n).
  • A is the fiddly one, and not because of the algorithm. The number of strings per line is never given — you must read the whole line and split it yourself. Say this out loud; it is where the time goes.
  • D is the one that separates the class: quadratic passes nothing, and int overflows silently.

Before the midterm

4 min

This is the last lecture before the midterm week. Everything up to here is examinable: complexity, the linear structures, binary search, the BST, the heap, and the three O(n log n) sorts.

Tell them what actually gets tested: not the recitation of algorithms, but picking the right one from the constraints. Given n ≤ 10⁵ and a "minimum maximum" phrasing — binary search on the answer. Given "next smallest, repeatedly" — a heap. That reflex is the semester so far.
