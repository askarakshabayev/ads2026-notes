Heap and Priority Queue

A tree that gives up almost everything a BST offers and keeps exactly one promise — the smallest element is at the root. In exchange it never degenerates, needs no pointers at all, and answers "give me the next one" in logarithmic time forever.

01

Less order, more guarantee

14 min board

What to say

  • Start from last week's failure: a BST built from sorted input becomes a list of height n. The heap cannot do that — and the reason is worth the whole beat.
  • The heap property is local and weak: every parent is ≤ both children. Nothing is claimed about siblings, nothing about left versus right.
  • Because the order is weak, the structure can be forced: a heap is always a complete binary tree — every level full except possibly the last, which fills left to right. Complete means height is always ⌈log₂n⌉. No degenerate case exists.
  • And a complete tree needs no pointers: store it in an array, children of i are 2i+1 and 2i+2, parent is (i−1)/2. Write those three formulas and leave them up.
  • Say what you gave up: you cannot search a heap. "Is 47 in here" is O(n), the same as a plain array. A heap answers one question only — what is the minimum.

For the board

left(i) = 2i + 1
right(i) = 2i + 2
parent(i) = (i − 1) / 2
// the heap [1, 3, 6, 5, 9, 8] is this tree:
//          1
//        /   \
//       3     6
//      / \   /
//     5   9 8

Check the property with them on this example: 1 ≤ 3, 1 ≤ 6, 3 ≤ 5, 3 ≤ 9, 6 ≤ 8. Note that 9 sits above nothing and below 3, yet 5 and 8 are smaller — that is allowed, and it is why a heap is cheap.

The line that makes it click: a BST is organised so you can find anything; a heap is organised so you can find the next thing. Different jobs, and most scheduling-shaped problems want the second.
02

Two repairs, that is all

22 min demo: heap stepper

What to say

  • Insert. Put the new value at the end of the array — the tree stays complete — then sift up: while it is smaller than its parent, swap. At most log n swaps.
  • Extract-min. The root is the answer. Move the last element into the root (complete again), then sift down: swap with the smaller child while it is bigger. Again log n.
  • Insist on smaller child. Swapping with the larger one silently breaks the property and the bug survives small tests. Step the demo on that deliberately if time allows.
  • Use the demo: insert a few values, then extract three times, and read the swap counter. It never exceeds the height.
  • Building from n values. Inserting one by one is O(n log n). Heapify — sift down from the last parent backwards — is O(n). Surprising enough to state; the proof is that most nodes are near the bottom and sift down almost nowhere.

For the board

void siftUp(int i) {
    while (i > 0 && a[(i-1)/2] > a[i]) {
        swap(a[(i-1)/2], a[i]);
        i = (i-1)/2;
    }
}

void siftDown(int i) {
    while (2*i+1 < n) {
        int j = 2*i+1;
        if (j+1 < n && a[j+1] < a[j]) j++;  // smaller child
        if (a[i] <= a[j]) break;
        swap(a[i], a[j]);
        i = j;
    }
}
The j+1 < n check is not optional — a node can have a left child and no right one. Dropping it reads past the end of the array, and on a judge that is either a wrong answer or a crash, depending on luck.

03

In practice you write one line

16 min board

What to say

  • Everything above exists in the standard library as std::priority_queue — and by default it is a max-heap, which catches people out every single year.
  • Write both forms on the board: the default, and the min-heap incantation with greater<>. Make them copy it; nobody remembers it under time pressure.
  • The operations are named differently from what we just built: push, top, pop, and pop returns nothing — read top() first.
  • For pairs, it sorts by .first then .second, which is usually exactly what you want for "cheapest first, then by index".
  • Say where it shows up later in this course: Dijkstra in lecture 13 is a priority queue with a relaxation step. Today is the prerequisite for that.

For the board

// max-heap — the default, surprises everyone
priority_queue<int> pq;

// min-heap — memorise this line
priority_queue<int, vector<int>, greater<int>> pq;

pq.push(5);
int x = pq.top();   // look
pq.pop();           // remove, returns void
Two traps in one: pop() on an empty queue is undefined behaviour, not an exception — check empty(). And if your answer comes out reversed, you almost certainly forgot greater<>.

The shapes worth naming

Repeated "take the two cheapest". Pull twice, combine, push the result back. That loop is problem B almost verbatim, and it is also how Huffman coding works.

Event simulation. Keep a queue of (time, event); pop the earliest, process it, push whatever it spawns. Problem C is this.

k smallest of something huge. Never build the huge thing. Seed the heap with the obvious candidates and expand only the popped one — problem E in one sentence.

Keep the k best seen so far. A max-heap of size k: push, and if the size exceeds k drop the top. O(n log k) instead of sorting everything.

Heap sort, since it is on the syllabus: heapify in O(n), then extract-min n times — O(n log n), in place, no extra memory. It loses to quicksort in practice on cache, which is next week's discussion.

Lab 5 — how it maps onto today

12 min ADS-Lab-05

What to say

  • Only five problems this week, and four of them are one priority queue each. Say that up front — it is the shortest lab of the semester.
  • B is the "take the two cheapest, put the result back" loop from beat 03. If they can write that loop, B is ten lines.
  • E is the one that needs thought: k-th smallest sum without building all the sums. There are n² sums and n can be large; the heap exists precisely so you never materialise them.
  • D is the heavy one — TL 3 s, and it is not on the defence. Tell them to attempt it last, or not at all if they are short of time.
  • At the defence you will be asked to show the sift, not the #include. Solving with priority_queue is fine and expected; not knowing what it does underneath is not.

What comes next

3 min

Lecture 6 is sorting — heap sort, which you can already derive from today, and quick sort, which is the opposite philosophy. The hook to leave them with: heap sort has a guaranteed O(n log n) and still loses to quicksort on real data. Ask them to guess why before the next class; the answer is cache, and it is the first time in this course where the machine, not the asymptotics, decides.

Homework is Lab 5. It is small — ask for B and C, both of which are the plain queue loop.
