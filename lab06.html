01

The quadratic floor

14 min demo: race

What to say

  • Everyone already knows bubble sort. Write it, count the comparisons — n(n−1)/2 — and put the number for n = 10⁵ on the board: five billion.
  • Then the reframing: with a judge doing ~10⁸ operations a second, n = 10⁵ is the wall. Below it quadratic survives, above it nothing quadratic ever passes. That single threshold decides most submissions in this lab.
  • Run the race demo. The point is not that O(n log n) wins — it is how early it wins. At n = 1000 the gap is already 100×.
  • Name the properties that will separate the algorithms later: stability (equal elements keep their relative order) and in-place (O(1) extra memory). Both come back in the lab.

02

Heap sort — yesterday, reused

16 min board

What to say

  • You already built this last week. Heapify the array in O(n), then extract the minimum n times. Done.
  • Its selling point is the one guarantee nothing else here offers: O(n log n) always, no bad input, no randomisation needed, and O(1) extra memory.
  • So ask the obvious question out loud — if it is guaranteed and in place, why is it not the default sort anywhere? Hold the answer until beat 04.
  • One honest caveat: heap sort is not stable. Two equal elements can come out in the opposite order, which matters the moment you sort records by one field.

For the board

// build in O(n): sift down from the last parent
for (int i = n/2 - 1; i >= 0; --i)
    siftDown(i, n);

// then repeatedly move the root to the end
for (int i = n - 1; i > 0; --i) {
    swap(a[0], a[i]);
    siftDown(0, i);
}

With a max-heap this sorts ascending in place — the largest goes to the back each round. Point out that the array is simultaneously a shrinking heap and a growing sorted tail.

03

Quick sort and its bad day

22 min demo: partition

What to say

  • One idea: pick a pivot, move everything smaller to its left and everything larger to its right, then recurse on both sides. After partitioning, the pivot is already in its final position — say that, it is the part students miss.
  • Partition is the only real code. Walk the demo once by hand at normal speed, then once more asking the room where the boundary index moves.
  • A good pivot halves the array — depth log n, total O(n log n). A bad pivot peels off one element — depth n, total O(n²).
  • Here is the trap worth the whole beat: if you always take the first element as pivot, then already sorted input is the worst case. The most natural implementation dies on the most natural data.
  • Two fixes, both one line: pick a random pivot, or median-of-three. Randomised quicksort has expected O(n log n) on every input, adversarial ones included.
  • Mention what the library does, because they will use it: std::sort is introsort — quicksort that counts its own recursion depth and switches to heap sort when it goes too deep. Quicksort speed with heap sort's guarantee. That is the answer to beat 02's question.

For the board

int partition(int l, int r) {
    int p = a[l + rand() % (r - l + 1)];   // random!
    int i = l, j = r;
    while (i <= j) {
        while (a[i] < p) i++;
        while (a[j] > p) j--;
        if (i <= j) swap(a[i++], a[j--]);
    }
    return j;
}
Strict versus non-strict. Writing a[i] <= p instead of < makes the pointers run past each other on an array of equal elements and the recursion never shrinks. An array of a million identical values is a legal test.
And the pivot by value, not by index. Storing the index and then swapping elements around means the pivot moves under you.

04

What you will actually write

16 min board

What to say

  • In a contest you write sort(a.begin(), a.end()) and move on. The lecture matters so you know when that is not enough.
  • Custom order is a comparator returning strictly less. Say the word strictly and mean it: a comparator that returns true for equal elements is undefined behaviour, and in practice it segfaults inside the library.
  • For "descending, ties by name ascending" show the two-line comparator with an explicit tie-break. Half of this lab is exactly that shape.
  • When you need equal elements to keep their input order, std::sort is the wrong tool — use stable_sort. That is next week's algorithm, and problem A here already needs the idea.
  • The floating-point warning, because problem F is waiting: never compare doubles with ==, and if the output is fixed to three decimals, sort by the rounded value, not the raw one, or two runs disagree on ties.

For the board

sort(v.begin(), v.end(),
     [](const Student& x, const Student& y) {
         if (x.gpa != y.gpa) return x.gpa > y.gpa;
         return x.name < y.name;        // tie-break
     });
The comparator must be a strict weak ordering. return x.gpa >= y.gpa; compiles, passes the samples, and then crashes on a big test. If a submission gets a runtime error only on large inputs, look here first.

Sorting without comparing

Two problems in this lab have a tiny value range, and there the O(n log n) bound does not apply at all — it only holds for comparison sorts.

// counting sort: 26 letters, |s| up to 10⁶
int cnt[26] = {};
for (char c : s) cnt[c - 'a']++;
for (int i = 0; i < 26; ++i)
    cout << string(cnt[i], 'a' + i);

That is O(n + k), and for problem I it is the difference between comfortable and borderline. Worth five minutes — it is the first time the class sees a sort that beats n log n.

05

Lab 6 — how it maps onto today

14 min ADS-Lab-06

What to say

  • Be straight with them about what this lab tests: not one problem here requires you to implement a sort. Every single one is solvable with std::sort plus the right comparator.
  • So the skill being drilled is beat 04 — reading the ordering rule out of the statement correctly. That is where the marks are lost, not in the algorithm.
  • Start them on I (counting sort) and D (dates as tuples). Both are short and both teach the comparator habit.
  • C has a genuine edge case worth mentioning: the minimum difference can be large, so initialise the running minimum properly — not with a guessed constant. Our own reference solution had this bug.
  • F and G are the heavy pair and neither is on the defence. F is weighted GPA with a grade table, rounding and tie-breaks at n = 10⁵; G is not really sorting at all.

What comes next

3 min

Lecture 7 is merge sort — the third row of the scoreboard, the one that is both guaranteed O(n log n) and stable, at the cost of O(n) memory. Leave the class with the question that next week answers: we have two O(n log n) sorts already, so what is merge sort for? The answer is stability and, more importantly, that the merge step itself solves problems sorting cannot.
