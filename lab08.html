01

Compute the place instead of finding it

16 min board

What to say

  • A BST finds a key in O(log n) by comparing. A hash table computes where the key must be and goes there — O(1), with no ordering at all.
  • That is the trade, and it is worth naming both halves: you gain constant lookup, you lose every ordered query. No "smallest", no range, no in-order output. That is why std::map still exists alongside unordered_map.
  • Collisions are not an edge case — with a table of size m and more than m possible keys they are guaranteed. Pigeonhole. The question is only how you handle them.
  • Two standard answers: chaining (each bucket is a list) and open addressing (probe the next free slot). Chaining is what the STL does; say it and move on.
  • The honest warning about unordered_map: worst case is O(n) per operation when everything lands in one bucket, and on Codeforces this is weaponised with anti-hash tests. map at O(log n) guaranteed is often the safer choice under time pressure.

What makes a hash function good

Deterministic — same input, same output, always. Otherwise nothing works.

Uniform — spreads keys across buckets. A function that maps every string to 0 is a valid hash function and a useless one.

Fast — computing it must be cheaper than the search it replaces.

Avalanche — changing one character changes the hash a lot. Otherwise similar keys collide in clusters.

Counter-example worth showing: "sum of the letter codes" satisfies the first three and fails the fourth badly — every anagram collides. abc, bca and cab all hash the same. Position must enter the formula, which is exactly what the next beat does.
02

Turning a string into a number

20 min demo: hash

What to say

  • The fix for anagrams is to weight each position differently: treat the string as a number in base p. That is the polynomial hash, and it is the only string hash this course uses.
  • Write the formula and the two constants: p a prime above the alphabet size (31 for lowercase letters), m a large prime modulus (10⁹+7 or 10⁹+9).
  • Compute it in the demo for a few strings, then deliberately find a collision with a tiny modulus. Seeing two different strings share a hash is what makes the probability talk land.
  • The birthday bound, stated plainly: with n strings and modulus m the chance of some collision is about n²/2m. At n = 10⁶ and m = 10⁹ that is roughly 1/2 — not negligible.
  • Hence double hashing: two different moduli, compare both. The effective modulus becomes ~10¹⁸ and the probability drops to nothing. Say that this is standard practice, not paranoia.
  • And the practical rule for this lab: if a hash solution gets a strange wrong answer on one big test and nowhere else, suspect a collision before suspecting the logic.

For the board

h(s) = (s₀·p⁰ + s₁·p¹ + … + sn−1·pn−1) mod m
const long long p = 31, m = 1e9 + 7;

long long h = 0, pw = 1;
for (char c : s) {
    h = (h + (c - 'a' + 1) * pw) % m;
    pw = pw * p % m;
}
Why c - 'a' + 1 and not c - 'a': without the +1 the letter a maps to 0, and then "a", "aa" and "aaa" all hash to 0. A whole family of strings collapses.
Overflow: h * p with both near 10⁹ reaches 10¹⁸, which fits long long — barely. Push the modulus higher and it does not. Take the modulus at every step, never at the end.

03

Any substring in O(1)

22 min demo: search

What to say

  • Precompute the hash of every prefix, and the hash of any substring becomes a subtraction. One O(n) pass buys O(1) queries forever after.
  • Write the substring formula carefully — the power factor is what trips everyone: h[r] − h[l−1]·p^(r−l+1), all modulo m, and add m before the final mod because the subtraction can go negative.
  • That negative-result bug is worth a full minute. In C++ (-5) % 7 is -5, not 2. A single missing + m gives wrong answers on perfectly ordinary tests.
  • Now Rabin–Karp is two lines: hash the pattern once, then compare it against the hash of every window of the text. O(n + m) instead of O(n·m).
  • Say the honest caveat: a hash match is probably a match. The textbook version verifies with a direct comparison; with double hashing, competitive programmers skip the verification. Both are defensible — name which one you expect at the defence.
  • Close the loop with the previous lecture: this is the second time we have replaced an O(n·m) scan with something linear, and next week does it a third way, deterministically, with no probability at all.

For the board

// prefix hashes, 1-indexed
h[0] = 0; pw[0] = 1;
for (int i = 1; i <= n; ++i) {
    h[i]  = (h[i-1] * p + (s[i-1] - 'a' + 1)) % m;
    pw[i] = pw[i-1] * p % m;
}

// hash of s[l..r], 1-indexed inclusive
long long get(int l, int r) {
    return ((h[r] - h[l-1] * pw[r-l+1]) % m + m) % m;
}                              // ↑ this + m matters
Two hashes, not one, whenever the string is long. Keep a second modulus (10⁹+9) and compare the pair. It doubles the code and removes the entire class of "correct but occasionally wrong" submissions.

Lab 8 — how it maps onto today

12 min ADS-Lab-08

What to say

  • Six problems, and they split cleanly: A and D are the formula itself — compute a hash, or invert one. Do those first, they need nothing beyond beat 02.
  • B is Rabin–Karp on two strings, straight out of beat 03. E and F are the prefix-hash machinery from the same beat, applied twice.
  • E asks for the number of distinct substrings at |s| ≤ 2000. Hashing all O(n²) substrings into a set is the intended solve, and the TL is 4 s precisely because of it.
  • C is the awkward one: the input is multi-test — an unknown number of blocks until the terminator. Read the format with them; more submissions die on that than on the algorithm.
  • Warn them the reference solutions for B and C use KMP, which is next week's technique. Either approach is accepted; solving them with hashes is the intended exercise.
